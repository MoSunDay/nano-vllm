## Q1：数字为什么会爆？RMSNorm 拉回来会不会失真？

### 学生问

- 数字为什么会爆？
- 如果数和数之间的差异本来就很大，用 RMSNorm 拉回来是不是就失真了？
- 那直接 clip 不就行了？（限制在 [-1, 1]）

### 老师答

**数字为什么会爆：**

矩阵乘法里，每一步的结果 = 前一步 × 权重。权重随机初始化，控制不了大于还是小于 1：

- 权重平均 > 1：`1.0 → 1.5 → 2.25 → ... → inf`（爆炸）
- 权重平均 < 1：`1.0 → 0.7 → 0.49 → ... → 0`（消失）

到第 10 层，后面那层收到的已经不再是"有意义的信息"了。

**RMSNorm 不会失真：**

RMSNorm 是"整体等比缩放"，不是"把每个数抹平"：

```
token A: [100, 0.01, -50]  RMS ≈ 64.5
→ [1.55, 0.0002, -0.77]

大的还是大，小的还是小，正的还是正，负的还是负。
比例关系完全保留。
```

可学习的参数 γ 解决了"有些维度天生就应该大"的问题：归一化负责"别爆"，γ 负责"该大的还得大"。

**Clip 为什么不行：**

| 方法 | 做了什么 | 信息保留 |
|------|---------|---------|
| Clip | 超出范围直接截断 | 丢失，不可逆 |
| RMSNorm | 等比缩放 | 保留，可逆（通过 γ） |

```
token A: 100 → clip → 1
token B: 2   → clip → 1
两个完全不同的值变成一样了，信息直接被扔掉。
```

### 关键收获

- RMSNorm = 整体等比缩放 + 可学习的逐维度缩放（γ）
- 不是抹平差异，而是把差异维持在一个安全的数值范围内
- 像"定速巡航"：不管上坡下坡，速度始终稳定

## Q2：模型怎么区分语序？长 Context 为什么会"忘"？

### 学生问

- 旋转是类似余弦相似度吗？
- 注意力缺陷会让 Context 太长以后出现忘记内容的现象，怎么解释？
- 不同模型的有效 Context 长度为什么不一样？
- 为什么需要拆分那么多对旋转？直接在空间里旋转不就行了？

### 老师答

**RoPE 的旋转和余弦相似度的关系：**

RoPE 旋转后，两个位置的 Q·K 点积 ∝ cos((i-j)θ)，只取决于相对距离。但 RoPE 的旋转和余弦相似度不完全一样——余弦相似度是两个向量之间的夹角，RoPE 是同一个向量被旋转了不同角度之后再去算点积。旋转是手段，目的是让"同一个词在不同位置"变成不同的向量。

**长 Context 为什么会忘——三层原因：**

| 原因 | 谁的问题 | 一句话 |
|------|---------|--------|
| 注意力稀释 | Attention（softmax 总和=1） | 人太多，每人分到的饼太小 |
| 两头强中间弱 | Attention（训练偏见） | 中间的信息最容易被忽略（Lost-in-the-Middle） |
| 远距离区分力下降 | RoPE（低频维度角度差太小） | 离得太远，旋转角度差太小，分不清了 |

**注意力总和为什么固定为 1：**

因为 softmax 的数学定义：`weights[i] = exp(scores[i]) / Σ exp(scores[j])`，分母是所有 exp 的总和，所以 Σ weights = 1，必然成立。设计成这样是因为 Attention 的输出是 weights · V（加权平均），总和 = 1 保证了输出在合理范围内且可以理解为"概率"。

**不同模型有效长度为什么不一样：**

有效 Context 长度 = f(训练长度, RoPE base, 外推技巧, 注意力方式, 模型规模)。同样的架构，调不同的参数、用不同的训练策略，出来的有效长度可能差 10 倍以上。

**为什么拆成多对 2D 旋转：**

高维空间里不存在"转一个角度"这种操作。高维旋转数学上只有一种标准做法——选两个维度组成一个平面，在那个平面里转。这不是 RoPE 发明的，是数学本身决定的。

每对旋转速度不同是为了捕捉不同尺度的距离信息：
- 高频对（旋转快）：相邻位置就能区分 → 负责近处精度
- 低频对（旋转慢）：很远才有变化 → 负责远处趋势

所有维度对用同一个角度转，提供的信息是重复的——就像问 512 个人同一个问题，得到的都是同一个答案。

### 关键收获

- RoPE 不是在 1024 维里转一个角，而是 512 个 2D 平面各自以不同速度旋转
- softmax 总和=1 是数学必然，也是长 Context 遗忘的根源之一
- 有效 Context 长度由训练、参数、技巧、模型规模共同决定
- 高维旋转只能拆成 2D 平面一对一对转，没有别的办法

## Q3：词和词之间怎么建立联系？Q/K/V、多头、参数怎么看？

### 学生问

- Q、K、V 分别是什么？
- 为什么需要那么多头？为什么是 32 不是 16 不是 8？K/V 为什么是 8？
- 为什么 4096 对应的是 7B？
- 量化模型为什么会出现乱码？量化影响注意力还是权重？
- MLP 是什么？和 Attention 是什么关系？

### 老师答

**Q/K/V 的角色：**

- **Q（Query）**："我想找什么"——主动的搜索关键词，去找和自己相关的其他 token
- **K（Key）**："我有什么信息"——被动的标签，等着别人的 Query 来匹配
- **V（Value）**："我的实际内容"——如果匹配上了，就把这些信息拿走

协作过程："吃"的 Q 和"猫"的 K 匹配度高 → 把"猫"的 V 按权重加到"吃"的向量里 → "吃"现在包含了"猫"的信息。

**为什么需要多个头：**

一个头的注意力只能学一种关注模式。但语言里词和词之间的关系是多种多样的（指代关系、语法关系、语义关系）。多个头 = 多个独立的"视角"，每个头各自学一种关注模式，最后拼在一起。

**为什么 Q 头数是 32：**

头数不是拍脑袋选的，是算出来的：

```
头数 = hidden_size / head_dim = 4096 / 128 = 32
```

- head_dim = 128：每个头的表达力足够（经验值，64~128 最佳区间）
- hidden_size = 4096：模型的总"脑容量"，由模型规模决定
- 头数是被动结果，不是主动选择

**K/V 头数为什么是 8（GQA）：**

32 组 K/V 里有大量冗余——相近的 Q 头学到的 K/V 模式很相似。压到 8 组（4:1 GQA），效果损失极小，但 KV cache 直接缩小 4 倍，decode 速度大幅提升。

**7B 怎么从 4096 算出来：**

```
每层参数：Attention ≈ 42M + MLP ≈ 135M ≈ 177M
36 层总计：177M × 36 ≈ 6.4B
加上 Embedding ≈ 623M
总计 ≈ 7B
```

hidden_size 决定"每层多大"，层数决定"堆多少层"，两者乘起来就是参数量。

**量化为什么乱码：**

量化影响的是权重精度（FP16 → INT8/INT4），不是某个组件的功能。但 Q/K/V 都是通过权重矩阵算出来的，权重精度下降 → QKV 有误差 → 注意力权重偏移 → 概率分布变形 → 采样选错字 → 自回归导致一连串全错。所有组件都在工作，只是每个都"差了一点点"，几十层累积起来就差了很多。敏感的层（Embedding、LM Head、首尾层）需要保持高精度。

**MLP 和 Attention 的关系：**

MLP = Multi-Layer Perceptron（多层感知器），本质是两层线性变换夹一个激活函数。在 Transformer Block 里和 Attention 是并列关系：
- Attention = 开会，让词和词之间交流信息
- MLP = 会后消化，每个 token 拿着收集到的信息自己加工
- MLP 中间维度（11008）比输入（4096）大，是为了在高维空间做非线性变换

### 关键收获

- Q/K/V 不是三个独立的网络，是一次矩阵乘法算出来后切三段
- 头数 = hidden_size / head_dim，是结构参数的被动结果
- GQA 压缩 K/V 头数是在推理速度和效果之间权衡，4:1 几乎无损
- 模型参数量 = 每层参数 × 层数 + Embedding，由 hidden_size 和层数共同决定
- 量化影响权重精度，误差跨层累积导致乱码，不是某个组件"坏了"
- Attention 负责"看哪里"，MLP 负责"怎么处理"，缺一不可

## Q4：为什么 100 层等于 1 层？SiLU 怎么解决？为什么不用 ReLU？

### 学生问

- 为什么 ReLU 的"小于0就变0"会导致神经元死亡？
- 为什么为 0 就是没信号、没梯度了？

### 老师答

**100层=1层的原因：**

矩阵乘法可以合并——100 个矩阵乘在一起等于 1 个矩阵。所以 100 层线性变换和 1 层没有任何区别，模型再深也学不到更复杂的东西。SiLU 在矩阵乘法之间插入非线性，"打断"了线性链，让每一层真正独立。

**ReLU 的两个致命问题：**

1. **神经元死亡**：负数输出全部变 0 → 梯度为 0 → 权重永远不更新 → 神经元永久"死亡"。不管负数多大或多小，输出都是 0，再也没机会学习。
2. **输出不连续**：在 x=0 处有折角，梯度突变，训练不稳定。

**为什么为 0 就是没梯度：**

训练时用链式法则从输出往回传梯度：

```
第3层的梯度 = 第4层传来的梯度 × 第3层的局部梯度
第2层的梯度 = 第3层传来的梯度 × 第2层的局部梯度
...
```

ReLU 在 x<0 时局部梯度 = 0。链式法则里乘了一个 0 → 梯度被掐断 → 前面所有层都收不到梯度 → 权重不更新。

两个层面都断了：前向传播输出 0（对结果没贡献）+ 反向传播梯度 0（权重不学习）。所以叫"死亡"。

**SiLU 为什么不会死：**

SiLU(x) = x × sigmoid(x)，负数区域输出是小的负数（不是 0），局部梯度是小的正数（不是 0）：

```
x = -1: SiLU = -0.27, 梯度 ≈ 0.073  （小但不是 0）
x = -5: SiLU = -0.035, 梯度 ≈ 0.007  （很小但仍然不是 0）
```

梯度传过去了，前一层还能更新权重，只是更新得慢。神经元还活着。

### 关键收获

- 0 是"死了"，0.073 是"很弱但还活着"
- ReLU 对负数下死手，SiLU 留一线生机
- 非线性激活的作用是"打断"线性链，让深层网络真正变深
- SiLU 比 ReLU 好：负数区域不截断（不死亡）、处处平滑（梯度稳定）

## Q5：采样器做什么？为什么现在的模型都推荐高 temperature？

### 学生问

- 温度小结果更确定，但是没有创造性了
- 为什么现在的 GLM、Qwen、Minimax、Kimi 几乎都会把温度拉很高？

### 老师答

**Sampler 的三步工作：**

1. 除以 temperature → 控制概率分布的"尖锐度"
2. softmax → 把分数变成概率（总和=1）
3. 从概率中选一个字 → 把"菜单"变成"菜"

没有采样器，模型永远只给概率数字，不给具体文字。

**Temperature 的本质是"确定"和"创造"的权衡：**

- T → 0：永远选最高概率，结果确定但无多样性（适合翻译、事实问答）
- T > 1：低概率词也有机会，有创造性但可能胡说八道（适合写诗、头脑风暴）
- 适度的随机性（T ≈ 0.6~0.8）在很多任务上反而比 T=0 效果更好，因为概率最高的词不一定是最对的

**为什么现在模型都推荐高 temperature：**

| 原因 | 为什么需要高 T |
|------|-------------|
| 对齐训练压平了概率分布 | RLHF/DPO 让概率分布变平，T=0 容易选错，需要温度拉开差距 |
| 避免重复循环 | 高 T 打破"重复→概率更高→继续重复"的死循环 |
| 聊天体验 | 用户想要多样性的回答，而不是一字不差的固定答案 |
| 思维链推理 | 探索过程需要尝试多条推理路径，T=0 只会沿一条路走到底 |

### 关键收获

- Sampler = 概率 → 具体选择的桥梁，没有它模型只给"菜单"不"上菜"
- 不是温度高了才好，而是对齐训练让概率分布变平了，高温度是补回来
- Temperature 是产品设计和技术的双重选择

## E1-E4：引擎层——怎么让推理跑得起来、跑得快

### 学生问

（无，老师直接展开讲解）

### 老师答

**E1 Scheduler（调度器）——控制流量，防止 GPU 崩溃：**

没有调度器时，100 个请求同时涌入 GPU，每个都要占 KV cache，显存不够就 OOM 崩溃。调度器控制"餐厅"流量：显存充足放更多请求，显存紧张让新请求排队。

调度策略：每轮要么全做 prefill（处理新请求的 prompt，计算量大），要么全做 decode（已运行的请求各生成 1 个 token，显存带宽瓶颈）。两者走不同的 GPU 代码路径，不混在一起。

显存不够时的抢占机制：把最早开始 decode 的请求踢回等待队列，释放 KV cache 给更需要的请求，被踢的请求下次重新 prefill。

**E2 BlockManager（块管理器）——KV cache 按需分配 + 前缀复用：**

没有块管理器时两个问题：
1. 空间浪费：预分配 2048 token 的空间但只用了 100 个，剩下的空着但别的请求用不了
2. 无法复用：两个请求开头一样，各自的 KV cache 分别存了一份一模一样的内容

解法：KV cache 切成固定大小的块（每块 256 token），按需分配。通过链式哈希（每个块的哈希依赖内容 + 前一个块的哈希）实现 prefix caching——相同前缀的块跨请求共享，第二个请求直接引用第一个请求已经算好的块，不用重新算。

**E3 Sequence（序列）——一个请求从生到死的完整档案：**

记录每个请求的：状态（WAITING/RUNNING/FINISHED）、进度（生成了多少 token）、预算（max_tokens）、结束条件（是否遇到 EOS）、位置信息（block_table）。调度器每轮扫描所有 Sequence 的状态来决定下一步做什么。

**E4 ModelRunner（模型执行器）——把调度决策翻译成 GPU 指令：**

三步工作：① 把多个请求的 token 拼成 tensor（prefill 用变长拼接，decode 每请求 1 token）→ ② 调用模型前向传播 → ③ 采样并拆分结果到各自的 Sequence。

性能优化职责：
- CUDA Graph：decode 每步做的事一样，提前"录制"操作序列，运行时直接"回放"，跳过 CPU 调度开销。按不同 batch size（1, 2, 4, ..., 512）预录制多个 graph
- torch.compile：自动融合小操作（如 RMSNorm 的五步合成一个 kernel），减少显存读写次数

**完整一次推理流程：**

```
用户发送请求
→ Scheduler 排队，创建 Sequence（WAITING）
→ BlockManager 分配 block
→ Scheduler 决策：本轮 prefill
→ ModelRunner：拼 tensor → Embedding → 36 层 Transformer → LM Head → Sampler 选出 token
→ Scheduler 后处理：Sequence 追加 token（RUNNING），BlockManager 更新 hash
→ 循环 decode 直到 EOS 或 max_tokens
→ Sequence FINISHED → BlockManager 回收 block → 返回结果
```

### 关键收获

- 九个组件（模型层 5 + 引擎层 4），每一个去掉都会导致功能缺失、性能崩溃或根本跑不起来
- 调度器平衡 prefill 和 decode 两类任务，显存不足时抢占早期请求
- BlockManager 解决 KV cache 的空间浪费（按需分配）和重复计算（prefix caching）
- ModelRunner 是调度器和 GPU 之间的"翻译官"，还负责 CUDA Graph 和 torch.compile 优化

## 深入话题一：Embedding / LM Head——文字和数字之间的翻译

### 内容

**为什么不能直接用编号：**

Tokenizer 把文字切成编号（"猫"→108386），但编号是人为分配的，编号之间的距离不代表语义关系（猫=1 和 汽车=2 距离近，但猫和鱼距离远，完全错误）。

**Embedding 怎么解决：**

一张巨大的查找表（151936 × 4096），把每个编号映射成一个 4096 维向量。这张表是可学习的——训练过程中模型自己调整，让语义相近的词在向量空间中靠得更近（猫和狗的向量变得接近，猫和汽车的向量变得远离）。

**LM Head 怎么翻译回来：**

模型 36 层算完后输出 4096 维向量，LM Head 用一个矩阵乘法映射到 151936 维 logits（词表大小），每个 token 一个分数。再经 softmax 变概率，Sampler 选出最终的字。

有趣的细节：LM Head 和 Embedding 的权重矩阵形状完全一样（151936 × 4096），很多模型共享同一份权重——"文字→向量"和"向量→文字"是同一映射的正反方向。

### 关键收获

- Embedding 让模型自己学会词与词的关系，而不是被编号强加错误关系
- 没有 Embedding 文字进不来，没有 LM Head 文字出不去

## 深入话题二：推理引擎的优化技术

### 内容

**推理的瓶颈是显存带宽，不是算力：**

decode 每步只算 1 个 token，但要读取所有历史 KV cache。"搬数据"比"算数据"慢。所以优化推理的关键是减少不必要的显存读写和 CPU 开销。

**CUDA Graph——减少 CPU 调度开销：**

decode 每步做的事一模一样，但 CPU 每次要发几百条 kernel launch 指令（每条约 5-10μs），CPU 调度开销比 GPU 计算时间还长。CUDA Graph 提前录制操作序列，运行时 CPU 只发一条"回放"指令。按不同 batch size 预录制多个 graph（1, 2, 4, ..., 512）。

**torch.compile——减少显存读写：**

模型里很多"小操作"（RMSNorm 有 5 步），每步各自读写一次显存。torch.compile 把它们融合成一个 kernel，数据在 GPU 寄存器中直接传递不写回显存：

| 组件 | 融合前 | 融合后 |
|------|--------|--------|
| RMSNorm | 5次读+5次写 | 1次读+1次写 |
| SiLU+乘法 | 3步各自读写 | 1个kernel |
| Sampler | 4步各自读写 | 1个kernel |

**Prefix Caching——避免重复计算：**

线上服务多个请求共享相同 system prompt 时，第一个请求算完 KV cache 后，后续请求直接复用，只算各自不同的部分。长 system prompt 场景下吞吐量提升几倍甚至十几倍。

### 关键收获

- 推理优化围绕"减少搬数据"展开，不是"算得更快"
- CUDA Graph 省的是 CPU 开销，torch.compile 省的是显存读写
- Prefix Caching 在实际线上场景收益巨大

## 深入话题三：模型怎么学会这些参数的——训练三阶段

### 内容

**模型一开始所有权重都是随机数**，训练就是不断调整这些随机数让输出越来越准确。

**阶段一：预训练——阅读整个互联网**

- 喂几万亿 token 的文本，目标是"给定前 N 个字，预测第 N+1 个字"
- 纠错过程：模型输出概率分布 → 和正确答案算差距（loss）→ 反向传播算梯度 → 调整权重 → 重复几万亿次
- 预训练后模型会"续写"但不会"对话"、不会"拒绝"、不会"按指令行事"
- 成本：几千张 GPU 跑几周，几百万~几千万美元

**阶段二：SFT（指令微调）——学会听指令**

- 喂人工标注的"指令-回答"对
- 方法一样（预测下一个字），但数据从"随便什么文本"变成"指令-回答对"
- SFT 后模型能按指令回答，但可能回答不当（用户问怎么偷东西，真的教你）

**阶段三：RLHF / DPO（对齐训练）——学会做人**

- 喂人类的偏好判断（回答A比回答B好）
- RLHF：训练一个"裁判"（奖励模型）给回答打分，根据分数调整模型
- DPO：不需要裁判，直接用对比学习让好回答概率升高、坏回答概率降低
- 对齐后模型懂得拒绝不当请求、回答符合人类偏好
- 但概率分布也变平了——这就是为什么现在模型需要高 temperature
- 成本：相对便宜，几张 GPU 可完成

### 关键收获

- 预训练成本最高（几千万美元），SFT 和对齐训练相对便宜
- 开源预训练模型珍贵——普通人做不起预训练，但可以在上面做 SFT + DPO 定制专属模型
- 三阶段训练 + 九个组件的完整图景：

```
训练：预训练（学会语言）→ SFT（学会听指令）→ RLHF/DPO（学会做人）
推理：文字 → Embedding → [RMSNorm → Attention(RoPE) → RMSNorm → MLP(SiLU)] × 36 → LM Head → Sampler → 文字
引擎：Scheduler 控制流量 → BlockManager 管显存 → Sequence 跟踪状态 → ModelRunner 执行优化
```
